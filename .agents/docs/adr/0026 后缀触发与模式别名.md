## 后缀触发与模式别名

侧问的触发符从「只看开头」扩到「开头或结尾」: `?`、`？`、`﹖`、`︖` 出现在末尾时剥掉一个触发符, 余下文本是问题. 只有没有前缀匹配器认领时才看后缀, 所以 `@foo?` 仍是文件搜索, `?为何?` 仍是前缀侧问且末尾问号是正文. 后缀判定只看最后一个字符, 后面再有空格就不算; 模式完全由当前查询决定, 末尾再打字就退回会话过滤, 面板不改写输入. 发问后锁定的输入行保留用户打的触发符与它所在的一端; 没有当前会话时照样认领, 只显示提示. 四个码点与 ADR 0024 的前缀集相同.

公开契约因此新增 `suffixMatcher`, 与 `prefixMatcher` 对称; 匹配器可以声明可选的 `mode` 别名, 让同一模式的两种写法在模式命令与 `getState().mode` 里仍是一个模式. ask 注册两个匹配器: 前缀 `ask` 优先级 10, 后缀 `ask-suffix` 优先级 5 并别名到 `ask`; 10 表示显式触发, 5 表示后缀, 兜底会话仍是 -1000. 本体只多了一个可选的 `mode` 字段与一次发布, 解析顺序仍是优先级, 不用加「前缀阶段/后缀阶段」的两遍解析; 代价是跨模块的优先级规则要写清: 后缀匹配器必须排在所有前缀触发器之后.

考虑过只给 ask 写一个手写 `match` (ADR 0018 本来就允许). 那样单匹配器与单一模式 id 都不用动, 但跨模块的「前缀优先」只能靠 ask 的模块 order 排在其它触发器之后这一巧合, 外部模块 order 更大时会被后缀截走, 通用能力也不在公开契约里. 也考虑过把后缀做成独立模式 id, 代价是模式命令在两种写法间不认为是同一模式, 公开状态出现两个 ask. 粘性锁存与把后缀改写成前缀都否决了: 前者让模式脱离输入文本, 后者在发问瞬间搬走用户刚打的字符, 退出还要删开头的标记.
