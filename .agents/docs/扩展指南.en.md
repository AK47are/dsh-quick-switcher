This file is for people who change this plugin or add a module to it: how the build artifact is produced, which fields a module declaration and the public service have, and how to extend the host side. A reader who only wants the usage guide can skip it.


## Build

esbuild bundles client.js from src/plugin.js into a single classic script, which is not committed and must not be edited by hand. After cloning the repository, install the dependencies first, and prepare generates it along the way:

```
npm install
```

Rebuild after changing the source:

```
npm run build
```

npm run check verifies that client.js matches src/ and reports a missing artifact or a stale one; npm test runs unit tests for the module interface and the registry, the settings store, the settings page model, module switches, entry commands, the default mode, copy merging, Matchers and views, prefix and suffix Matchers, mode aliases, the row modules, input history, side questions, the side question model catalog and effort resolution, filtering and focusing in the side question settings menu, side question answer rendering and view copy, new-workspace path parsing and its view, the host directory endpoints, host routes, search, time, path helpers, session IDs, the pointer, digit jump, panel keys, archive matching and restore, and the contract of the nine modules. module.js is also published separately as `./module` and reused by internal modules, so its implementation is bundled into client.js too.



## Extending

The nine lists are all modules now, under src/modules. To add a list, command or setting, create a directory in src/modules, declare a client module and add the definition to src/modules/client-manifest.js; to add a host endpoint, declare a host module with defineHostModule(id, setup) and add it to src/modules/host-manifest.js. The panel shell, the other modules and the core need no change.

A module declaration runs once at load, receives a static capability package (`id`, `t`, `settings`, `panel`, `shared`, `services`, `get`, `effect`, `log`) and returns these contributions:

- matchers: input claiming and views; each Matcher has id, priority, match and view, and an optional mode lets several spellings share one mode; a prefix is built with prefixMatcher and a suffix with suffixMatcher, each taking a string or an array of strings where the first hit wins; a suffix Matcher must rank below a prefix trigger so an explicit prefix claims first; a regular expression or whole sentence semantics is still written in match
- mount: created once per panel open, returning providers, matchers and dispose; an extra field on the mount surface goes to that module's Providers and content renderer as instance
- entry: the entry for the direct command, shaped `{ seed, mode?, labelKey?, aliases?, defaults? }`; the core uses it to register `quickSwitcher.mode.<模块>` automatically and lists the module as a candidate for the default mode
- descriptionKey and dependencies: the one sentence description on the module switch row in Settings, and which modules' published data this one reads; Settings warns when a dependency is off, without interlocking
- settings: fields declared as `[模块, 分组?, 字段]`, which Settings shows automatically; a custom field's render returns a React element and may close over the module api to read remote data; a custom field may declare `layout: "stack"` to use the full row, which suits wide controls such as a storage meter
- locale: the module's own Chinese and English dictionaries
- commands: commands registered with the DSH shortcut table
- slots: register any DSH Slot, such as the bridge in the session composer
- views: register content and footer renderers by kind, and a renderer receives `{ descriptor, instance, panel, t }`; `t` is the translation function of the module that registered the kind, falling back to core copy on a missing key
- keydown: optional on a view. A list view's keydown runs before the panel's Tab, arrow, Enter and digit handling and returns true when it consumed the key; the third argument is the highlighted row. Tab is handed to a list view only while the input owns the caret; with focus on the close button it still cycles. A content view's keydown still runs after the panel keys and owns its own letter gestures

The host side has its own src/modules/host-manifest.js, and a host module contributes webServer routes and event listeners through routes and listeners.

A module may import src/core and its own files only, never another module. To use data another module owns, call `api.shared.store(name)`: the sessions module publishes session-data and the workspaces and archive modules read the same entries.

A minimal Matcher looks like this:

```js
import { defineModule } from "../../core/module.js";

export default defineModule("my-mode", (api) => ({
  apiVersion: 1,
  order: 80,
  descriptionKey: "description",
  entry: { seed: ":" },
  locale: {
    zh: { title: "我的模式", description: "关闭后不再出现在面板。" },
    en: { title: "My mode", description: "When off, it stops appearing in the panel." },
  },
  mount(panel) {
    return {
      matchers: [
        {
          id: "my-mode",
          priority: 10,
          match: (query) => (query.startsWith(":") ? { filter: query.slice(1) } : null),
          view: (state, panel) => ({
            placeholder: "搜索",
            rows: [],
            emptyText: "没有匹配",
            hints: [{ keys: ["Esc"], label: api.t("hintClose") }],
            count: "",
          }),
        },
      ],
      dispose() {},
    };
  },
}));
```



## Public service

Another client plugin can register modules too without changing this plugin. Declare `inject: ["quickSwitcher"]` and register a module definition built by defineModule in apply:

```js
import { defineModule } from "dsh-quick-switcher/module";

export const inject = ["quickSwitcher"];

export function apply(ctx) {
  ctx.effect(() =>
    ctx.quickSwitcher.register(
      defineModule("my-mode", (api) => ({ /* 与上面的模块声明相同 */ })),
    ),
  );
}
```
